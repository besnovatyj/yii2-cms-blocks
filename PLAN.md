# Yii2-CMS Blocks — план: типизированные блоки

Сейчас блок — это HTML из редактора, который выводится в месте темы. План добавляет блоку **тип**:
схему полей и шаблон вывода. Тогда в место можно положить не только HTML, но и «три карточки в ряд»,
«изображение с текстом поверх», «витрину спектаклей», «чужой виджет». Менеджер заполняет форму, а
разметку рисует шаблон типа.

Первый потребитель — главная страница сайта. Её содержимое — набор блоков разных типов в месте `home`.

Мировые аналоги подхода: Wagtail StreamField, ACF Flexible Content, Drupal Paragraphs, Craft Matrix,
Statamic Replicator, Strapi Dynamic Zones.

## Решения (зафиксированы)

- **Блоки развиваются, а не заменяются.** Порядок, окно показа, кэш, каталог мест и админка
  остаются. Сегодняшний HTML-блок — это тип `html`.
- **Блок не знает, на какой странице он выводится.** Место в разметке объявляет тема. Главная — это
  Page `main` с вариантом представления `home`, а `home.php` выводит `BlockArea::widget(['area' => 'home'])`.
  Модуль Page не меняется. `$page->content` на главной не выводится: страница даёт главной SEO-поля
  (`meta`), а вступительный текст при желании оформляется отдельным блоком `html`.
- **Миграция переписывается** (create, без alter). Для рабочей базы — SQL, см. раздел «SQL для рабочей
  базы».
- **Чужие виджеты — двумя типами:** типы под конкретного провайдера (менеджер вводит только ID) и
  сырой `embed` под отдельным разрешением.
- **Поиск по блокам не нужен.** Извлечение текста из `data` не делаем.

Задел на будущее (сейчас не делаем): свои секции у любой страницы через общий вариант
`sections.php`, который выводит место `page-{id}` (ключ по id, а не по slug: переименование не отвяжет
блоки). Для этого каталог мест должен научиться объявлению по шаблону (`page-*`).

## Модель

### Тип блока

Тип блока — это:

- **id** — латиница, уникален в реестре;
- **label** и **hint** — для админки;
- **схема полей** — массив описаний полей (ниже);
- **шаблон вывода** — view-файл (алиасный путь);
- **поставщик данных** (необязательно) — класс, который по данным блока отдаёт переменные для шаблона.
  Нужен типам вроде «афиши» и «последних постов».

Источники типов:

| Источник                   | Как объявляет                                                         | Примеры                                      |
|----------------------------|-----------------------------------------------------------------------|----------------------------------------------|
| Модуль блоков (встроенные) | в коде модуля                                                         | `html`, `embed`                              |
| Тема                       | `themes/{тема}/blockTypes/{type}/schema.php` + `view.php`             | `cards-3`, `image-overlay`, билетный виджет  |
| Контентный модуль          | контракт `BlockTypeProvider` (`instanceof`-скан через `ModuleFinder`) | витрина спектаклей, последние посты, галерея |

Тема может переопределить шаблон типа из модуля, положив `blockTypes/{type}/view.php`. Это тот же
принцип, что с виджетами пакетов: пакет не правится, тема подменяет представление.

При совпадении id тип темы и тип модуля не сливаются: побеждает тот, что объявлен раньше по порядку
«встроенные → модули → тема», а в лог уходит предупреждение. Переопределять можно только
представление, не схему.

### Схема полей

```php
// themes/berdrama/blockTypes/cards-3/schema.php
return [
    'label' => 'Три карточки в ряд',
    'hint'  => 'Изображение, подпись и ссылка у каждой карточки.',
    'fields' => [
        'heading' => ['kind' => 'text', 'label' => 'Заголовок раздела', 'required' => false],
        'cards'   => ['kind' => 'repeater', 'label' => 'Карточки', 'min' => 1, 'max' => 3, 'fields' => [
            'image'   => ['kind' => 'image', 'label' => 'Изображение', 'required' => true],
            'caption' => ['kind' => 'text', 'label' => 'Подпись'],
            'link'    => ['kind' => 'link', 'label' => 'Ссылка'],
        ]],
    ],
];
```

Виды полей первой очереди:

| kind       | Значение в `data`             | Форма                                          | Замечание                                     |
|------------|-------------------------------|------------------------------------------------|-----------------------------------------------|
| `text`     | строка                        | input                                          | `maxlength` из схемы                          |
| `textarea` | строка                        | textarea                                       |                                               |
| `richtext` | HTML                          | `EditorWidget`, сниппеты, ФМ на папке блока    | текстовые шорткоды разворачиваются при выводе |
| `image`    | `{file, alt}`                 | выбор файла в проводнике на папке блока + alt  | `file` — путь относительно папки блока        |
| `link`     | `{url}` или `{route, params}` | цели из `MenuTargetProvider` или свободный URL | цель по route переживает смену slug           |
| `select`   | строка                        | dropDownList из `options` схемы                | позиция текста, тон фона и т.п.               |
| `checkbox` | bool                          | checkbox                                       |                                               |
| `repeater` | список объектов               | строки с полями, добавить/удалить/переставить  | `min`/`max`                                   |
| `code`     | строка                        | textarea, моноширинный шрифт                   | только у `embed`, см. шаг 5                   |

### Хранение

Таблица `{{%blocks_blocks}}` после переписывания миграции:

| Колонка                                        | Тип                  | Было                          |
|------------------------------------------------|----------------------|-------------------------------|
| `id`                                           | PK                   | =                             |
| `area`                                         | string(64)           | =                             |
| `type`                                         | string(64), not null | **новая**                     |
| `title`                                        | string(255)          | =                             |
| `data`                                         | JSON, not null       | **новая**, заменяет `content` |
| `status`, `show_from`, `show_to`, `sort_order` |                      | =                             |

Индексы: `(area, sort_order)`, `status` — как были.

- Сегодняшний `content` переезжает в `data` как `{"html": "…"}` с типом `html`.
- **Тип задаётся при создании и не меняется.** Данные разных типов несовместимы, а смена типа «на
  лету» молча теряла бы поля.
- Схема со временем меняется. Нормализатор читает `data` по текущей схеме: отсутствующее поле получает
  значение по умолчанию, лишнее игнорируется при выводе и выбрасывается при следующем сохранении.
  Версии схем не заводим.

### Файлы блока

По соглашению «у сущности своя папка», как у Page:

- `Module::directories()` → `['@static/origin/Blocks', '@static/cache/Blocks']`, `params.directories = true`;
- папка `@static/origin/Blocks/{id}` создаётся сервисом при создании блока и удаляется вместе с ним
  (образец — `PageManageService::createFolder()/removeFolder()`);
- форма открывает файлы только после первого сохранения, как в Page («Сохраните, чтобы…»);
- **все** файловые поля блока, включая редактор `html`/`richtext`, открывают проводник со scope на эту
  папку. Сейчас редактор блоков вызывается без `fmDefaultPath`, это исправляется попутно;
- у блоков, созданных до переписывания, папки нет. Её создаёт `actionUpdate`, если папки нет
  (только админка, на фронте лишнего I/O не появляется). Отдельный шаг выкладки не нужен.

### Вывод

```
BlockArea::widget(['area' => 'home'])
  → AreaReadModel: включённые блоки места (кэш APCu, тег `blocks`), окно показа — на каждый запрос
  → для каждого блока BlockRenderer:
      тип из реестра → нормализация data по схеме → [поставщик данных] → renderFile(view)
```

- Строка кэша получает `type` и `data` вместо `content`.
- **Тип неизвестен** (сменили тему, удалили модуль) → блок пропускается, в лог уходит предупреждение.
  Админка показывает такой блок с пометкой, как сейчас показывает блок в необъявленном месте.
- Готовый HTML блоков в кэш **не кладём**: у типов модулей данные живые (афиша), и кэшировать их
  должен сам поставщик данных. Шаблоны типов темы дешёвые.
- Текстовые шорткоды разворачиваются в полях `richtext` и в `html`, как сейчас. Виджетные — нет.
- `inline` у `BlockArea` остаётся и действует только на тип `html`.
- Каркас вокруг каждого блока не навязывается. Шаблон типа сам решает, нужна ли ему `<section>`.
  Если окажется, что каждому типу нужна одинаковая обёртка, место сможет задать её в `areas.php`.
  Это решение откладывается до шага 6, когда будут видны реальные типы.

### Места и разрешённые типы

`areas.php` получает необязательный ключ `types`:

```php
'home' => [
    'label' => 'Главная',
    'hint'  => 'Разделы главной страницы сверху вниз.',
    'types' => ['html', 'cards-3', 'image-overlay', 'intickets', 'embed', 'performance-showcase', 'blog-latest'],
    'sort'  => 5,
],
```

Ключ `types` не задан — в месте разрешён только `html`. Так все сегодняшние места (подвал, полосы,
окно) работают как раньше без правки.

## Порядок реализации

### Шаг 1 — Контракты (`yii2-cms-contracts`)

Зеркало `SnippetProvider`/`MenuTargetProvider`: нейтральные DTO без проектной специфики.

- `block/BlockType` — DTO: `id`, `label`, `hint`, `fields` (массив схемы), `view` (алиасный путь),
  `dataProvider` (FQCN строкой или null).
- `block/BlockTypeProvider` — `blockTypes(): BlockType[]`. Реализуется классом Yii-модуля.
- `block/BlockDataProvider` — `provide(array $data): array`: переменные для шаблона типа.
- `theme/ThemeBlockTypeCatalog` — каталог типов активной темы (аналог `ThemeAreaCatalog`).
- `theme/ThemeArea` — новое необязательное поле `types: list<string>|null`. Параметр с умолчанием
  в конце конструктора, так что это не BC-break: minor-версия.

### Шаг 2 — Пакет тем (`yii2-cms-themes`)

- `ThemeAreasReader` читает `types`.
- `ThemeBlockTypesReader implements ThemeBlockTypeCatalog`: обходит `blockTypes/*/schema.php`
  активной темы, `view` = `@themes/{тема}/blockTypes/{type}/view.php`. Memo на запрос. Каталог нужен
  и фронту (рендер), поэтому — **кэш в APCu** с тегом, сброс при recompile. Механизм сброса уточняется
  на этом шаге по тому, как пакет тем уже кэширует pathMap.
- DI-биндинг в `config/common.php`, как у `ThemeAreaCatalog`.
- Отдельно — переопределение шаблона типа модуля: «есть `blockTypes/{type}/view.php` без
  `schema.php`» — значит тема подменяет только представление.

### Шаг 3 — Ядро модуля (этот пакет)

- Переписанная миграция `m261002_100000_create_blocks_blocks_table` (имя то же: в истории
  миграций рабочей базы она уже отмечена применённой).
- `entities/Block`: `type`, `data` (массив; JSON-кодирование в AR), без `content`.
- `blockTypes/`: встроенные типы `html` и `embed` (схема + view в `src/views/blockTypes/`).
- `services/BlockTypeRegistry`: встроенные + модули (`ModuleFinder`) + каталог темы (DI, опционально).
- `schema/`: разбор схемы в объекты полей, нормализатор `data`, правила валидации по видам полей.
- `services/BlockRenderer` + обновлённые `AreaReadModel` и `BlockArea`.
- Readme: новый раздел «Типы блоков».

### Шаг 4 — Админка (этот пакет)

- Создание: место → **выбор типа** (карточки с label/hint, только разрешённые местом) → название → сохранить.
  После сохранения появляется форма полей. Это тот же поток, что сейчас: create → redirect на update.
- `forms/backend/BlockForm` — общие поля. `forms/backend/BlockDataForm` строится по схеме типа.
  Обе формы на `BaseForm`.
- Поле `image`: кнопка выбора открывает проводник v2 со scope на папку блока. **Проверить**, есть ли
  у `ExplorerWidget` режим «выбрать файл и вернуть путь». Если нет — это запрос на правку
  `yii2-cms-file-manager`, отдельным согласованием.
- Поле `link`: выпадающий каскад целей `MenuTargetProvider` (как в модуле меню) плюс свободный URL.
  **Проверить**, можно ли переиспользовать каскад модуля меню, а не писать свой.
- Поле `repeater`: см. открытый вопрос 1.
- Список блоков места: тип, название, статус, окно показа, порядок. Блоки неизвестного типа — с
  пометкой. Сырой HTML `embed` в админке **никогда не рендерится**, только текстом.

### Шаг 5 — Чужие виджеты

**Тип `embed` (встроенный).** Поле `code`, вывод на фронте как есть.

- Создание и правка кода — только при разрешении. RBAC в проекте маршрутный (`AccessAuthorizer`),
  поэтому разрешение — это псевдомаршрут, например `/Blocks/backend/default/embed`, который
  проверяется в контроллёре и форме. Без разрешения блок `embed` можно видеть, включать, выключать и
  переставлять, но не открыть его код на правку и не создать новый.
- В админке код показывается только текстом (см. шаг 4).
- CSP фронта: внешние домены виджета нужно разрешить. См. открытый вопрос 4.

**Типы провайдеров (в теме).** Например `blockTypes/intickets/`: схема — одно-два поля (ID, высота),
скрипт и разметку рисует шаблон. Сломать такой блок нельзя, разрешение не требуется.

### Шаг 6 — Главная (тема berdrama)

- `areas.php`: место `home` со списком `types`.
- `modules/Page/views/frontend/page/view.variants/home.php` + строка в `_labels.php`.
- Первые типы темы: `cards-3`, `image-overlay`, тип первого билетного провайдера.
- SCSS типов по правилам темы (tokens → адаптер → Bootstrap).
- Демо-страница в `themes/berdrama/docs/`, как требуют правила темы.
- В админке: у Page `main` выбрать вариант «Главная (блоки)». Это делает пользователь.

### Шаг 7 — Типы от контентных модулей

По одному пакету за шаг, каждый — по отдельному согласованию:

- Performance — витрина спектаклей (поля: заголовок, количество, фильтр);
- Blog — последние посты (заголовок, количество, рубрика);
- Gallery — галерея (выбор галереи).

Модуль реализует `BlockTypeProvider`, данные отдаёт его readModel через `BlockDataProvider`, кэш — на
стороне модуля. Шаблон по умолчанию лежит в пакете, тема переопределяет его своим.

| Пакет                                                       | Шаг | Что меняется                                                                        |
|-------------------------------------------------------------|-----|-------------------------------------------------------------------------------------|
| `yii2-cms-contracts`                                        | 1   | `block/*`, `theme/ThemeBlockTypeCatalog`, поле `ThemeArea::$types` — minor          |
| `yii2-cms-themes`                                           | 2   | чтение `types`, ридер `blockTypes/`, DI-биндинг — minor                             |

| `yii2-cms-performance`, `yii2-cms-blog`, `yii2-cms-gallery` | 7   | `BlockTypeProvider` + шаблоны — по запросу                                          |

## Решения, принятые при реализации шагов 1–4

Уточняют разделы выше; где расходятся — действует этот раздел.

- **Id типа модуля — `{moduleId}:{id}`.** Префикс ставит модуль блоков. По нему вывод находит
  модуль-владельца напрямую (`getModule`), без перебора модулей на каждый показ страницы; столкновений
  с типами темы нет. Порядок «встроенные → модули → тема» остаётся только для списка в админке, тип
  темы с id встроенного игнорируется с предупреждением.
- **Шаблоны модульных и встроенных типов тема перекрывает штатным overlay**
  (`themes/{тема}/modules/{ModuleId}/views/blockTypes/…`), а не своим механизмом в `blockTypes/`.
- **Встроенные `html` и `embed` разрешены в любом месте** (ответ 5). `ThemeArea::$types` — список
  типов сверх встроенных, по умолчанию пустой.
- **Каталог типов темы без кэша.** Вывод читает один `schema.php` по id (`is_file` + `require` под
  OPcache), обход каталога нужен только админке.
- **Repeater:** HTMX добавляет строку, перестановка и удаление — перемещением элементов в DOM (порядок
  полей в POST и есть порядок строк). Вложенных repeater нет; `richtext` и `code` внутри строки
  недоступны: редактор во вставленном HTMX фрагменте надёжно не поднять.
- **Изображение:** picker проводника v2 (`ExplorerWidget`, `returnAttribute = path`, scope на папку
  блока) — правка `yii2-cms-file-manager` не понадобилась. Миниатюр нет (ответ 2).
- **Ссылка:** плоский список целей `MenuTargetProvider` (свой `LinkTargets`, без зависимости от модуля
  меню) плюс свой URL с белым списком схем.
- **Разрешение `embed`:** псевдомаршрут `/Blocks/backend/embed/edit`. Без него блок с кодом можно
  переносить, включать и переименовывать, но данные из POST не принимаются, код показывается текстом.
- **CSP не трогаем** (ответ 4).

## SQL для рабочей базы

Имя миграции не меняется, поэтому таблицу `migration` трогать не нужно. Если у таблиц есть префикс —
подставить его к `blocks_blocks`.

```sql
ALTER TABLE `blocks_blocks`
    ADD COLUMN `type` VARCHAR(64) NOT NULL DEFAULT 'html' COMMENT 'Тип блока' AFTER `area`,
    ADD COLUMN `data` JSON NULL COMMENT 'Данные блока по схеме типа' AFTER `title`;

UPDATE `blocks_blocks` SET `data` = JSON_OBJECT('html', `content`);

ALTER TABLE `blocks_blocks`
    ALTER COLUMN `type` DROP DEFAULT,
    MODIFY COLUMN `data` JSON NOT NULL COMMENT 'Данные блока по схеме типа',
    DROP COLUMN `content`;
```

Порядок выкладки: SQL и код одним заходом. Ключ кэша сменён (`blocks.active.v2`), поэтому новый код
кэш старого формата не читает и отдельный сброс не нужен. Старый код между SQL и выкладкой работает,
пока жив его кэш, а без кэша упадёт на отсутствующем `content`. Папки старых блоков создаются при первом открытии
формы; базовые `@static/origin/Blocks` и `@static/cache/Blocks` — там же (рекурсивно) или
переустановкой модуля.

## Открытые вопросы

1. **Repeater в админке:** HTMX (сервер отдаёт строку, без npm-сборки; HTMX в админке разрешён) или
   TS-виджет в `assets/` модуля на esbuild (перестановка перетаскиванием без запросов). Склоняюсь к
   HTMX + кнопки «вверх/вниз»: перетаскивание для 3–6 строк не нужно.
2. **Миниатюры изображений блоков:** на первом этапе выводится оригинал с `width/height`. Нужен ли
   ресайз и `srcset` (`@static/cache/Blocks`)? Если нужен — где взять готовый механизм: в
   `yii2-cms-images` миниатюры привязаны к AR-изображениям, а не к файлу.
3. **Какие билетные и прочие провайдеры** нужны для типов шага 5 (Intickets, Radario,
   ПРО.Культура, ВК-видео…)?
4. **CSP фронта:** где сейчас задаётся политика (во фронте есть `CspReportController`) и как
   добавлять домены провайдеров: в конфиге приложения или вкладом типа блока.
5. **`embed` вне главной:** разрешать ли его в других местах или только в `home`.
